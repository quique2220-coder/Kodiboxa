# KODIBOXA: access, secrets and review protocol

## Review-only scope

These files provide code-review guidance, not authorization to change the repository,
configure integrations, run production operations, approve or merge a PR, or apply fixes.
Report findings and suggested corrections for human review. Do not infer automation
settings from the presence of this directory.

## Reporting standard for all KODIBOXA reviews

- Review the changed behavior and affected callers, not just the changed lines.
- Prioritize authorization bypass, credential exposure, data loss, duplicate side
  effects and broken user journeys over style preferences.
- Each finding must identify the affected code, a concrete failure scenario, the
  affected role, user impact, a minimal correction and a focused verification.
- Separate observed evidence from assumptions. Ask for clarification when a
  requirement is unclear; do not invent a vulnerability or an implementation.
- Distinguish a defect from a missing test. Do not claim a browser journey,
  physical device, external provider or production behavior was tested without evidence.
- Do not present mocked tracks, synthetic speech, snapshots or successful type checks
  as proof of real-device audio/video quality or transcription accuracy.
- Do not log or reproduce secrets, tokens, raw pass credentials, payment data,
  attendee contact information or transcripts in review comments.

## Server-side authorization

- Treat the authenticated server identity and current database role as authoritative.
  Reject client-supplied user IDs, roles, presenter assignments or registration status
  as authorization evidence.
- A frontend role switch changes the view, not the user's permissions.
- Check object ownership and event/session relationships on every protected operation,
  including polling, exports, generated credentials and reconnects.
- An administrator can present a session explicitly assigned to them without losing
  their admin role. Other admin session connections remain receive-only monitors.
- Participants need a confirmed registration for the event containing the session.
  A valid identity alone is not sufficient.
- Never allow a public preview or demo record to perform a real authenticated mutation.
- Preserve one-time bootstrap behavior: a revoked administrative role must not be
  silently restored on subsequent requests.

## Secret boundaries

- LiveKit signing secrets, Clerk server secrets, Stripe credentials and provider
  credentials must stay on the server. Flag exposure through Vite variables,
  bundles, responses, error messages, logs, source maps or repository files.
- Session access tokens must be short-lived, scoped to the authorized session and
  generated by the backend after authorization. Do not persist them in browser storage.
- Do not request access to production credentials or attendee data to conduct a review.

## Starting points

Trace changes through `artifacts/api-server/src/lib/auth.ts`,
`artifacts/api-server/src/lib/livekit.ts`, the relevant route, and its frontend caller.
Follow current imports rather than assuming these files contain every access decision.
